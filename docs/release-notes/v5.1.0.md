**v5.1.0: a warning when LEM will misread a results-CSV line.**
Every result, report, results-CSV line and QBench upload is what v5.0.1
produced. The hub now tells you when a line it wrote to the results CSV
will be read differently by LEM; it does not change or hold back the line.

**Commas, double quotes and line breaks**

- The results CSV line the hub writes for LEM is correct CSV, as v1's was:
  a value with a comma, a double quote or a line break is put in quotes.
  LEM's reader does not understand CSV quoting. It splits the text at every
  line break into rows, splits each row at every comma, and keeps the
  quote characters. So:
  - a **comma** (`40304, rerun`) moves every later value one column to the
    right, and LEM reads the Lab ID as `"40304`;
  - a **double quote** (`Q"A`, or an inch mark as in `Pipe 2"`) reaches LEM
    with the CSV quotes around it: LEM reads the Lab ID as `"Q""A"`;
  - a **line break** (a carriage return, a new line, or one of the rarer
    characters Python treats as a line boundary: `\v`, `\f`, `\x1c`,
    `\x1d`, `\x1e`, `\x85`, `\u2028`, `\u2029`) splits the row, and LEM may
    record the second part as a row of its own.
- What happens next is up to LEM. It looks a reading up in LabCore by the
  Lab ID it read, after any Lab ID cleanup set up for that GC in LEM. If no
  sample has that ID, LEM holds the reading. If another sample has it, the
  reading is filed on that sample.
- This applies to every value in the line, not only the Lab ID. A
  comparison standard whose name contains a comma (it appears in Best Fit)
  moves Fit Score and Source File. The stored file name in Source File
  contains the sample name, so a comma in the Lab ID is usually there too.
- When the hub writes such a line, it still writes it, byte for byte as
  before, and:
  - **marks the sample for review.** The note names each value with the
    problem, says what LEM will read the Lab ID as (with line breaks shown
    escaped, `\n`, never as a real line break), what follows from it, and
    what to do, for example: *Review: Lab ID '40304, rerun' contains a
    comma; Source File contains a comma. LEM splits each line at every
    comma and line break and keeps CSV quotes, so it will read the Lab ID
    as '"40304' and every value after the Lab ID one column off. If that ID
    (after any Lab ID cleanup set up in LEM) matches no LabCore sample, LEM
    holds the reading; if it matches another sample's ID, the reading is
    filed there. Rename the sample in QBench/LEM by hand. Once LEM is right
    there is nothing more to do in the hub; this note stays as a record.*
    When only another value is affected, the advice is "Check this reading
    in LEM by hand."
  - **raises one notification** with the same text, starting "Sample 412
    on GC-1:". Its link, **Open sample**, opens that sample.
- The hub cannot rename a sample, and there is no way to dismiss a review
  note in the hub. The note is information: once the sample is renamed in
  QBench and the reading corrected in LEM, nothing more needs doing here.
- **When it is checked:** whenever the hub writes a results-CSV row: a new
  result, a Re-process, Export to LIMS and a backfill release. A sample is
  notified once; exporting or re-processing it again adds the row as usual
  but no second notification. A late-blank note and the LEM note are kept
  side by side, and a Re-process with the current blank clears only the
  late-blank part. A folder load still counts only new late-blank notes.
- **Not checked:** results imported from v1's CSV (they write no row to the
  results CSV), and rows written before v5.1.0. A sample exported earlier
  is flagged the next time it is exported.

**Review notes on the Samples list**

The Samples list now shows a sample's review note on its row, shortened to
one line (hover for all of it); the sample's header shows it in full. This
covers every review note, not just the new one: an earlier-injected blank
that arrived late, a possible match with an imported result whose time
can't be checked, a CDF method not mapped for the instrument, and a blank
whose file was replaced. Before, the list showed none of them. The classic
page shows them as before (the Review badge).

**Correction to the v2.0.0 notes**

The v2.0.0 notes said "The lab ID is the CDF's sample name with outer
whitespace stripped." That is true inside the hub: the stored Lab ID, the
Samples page, search, `/lab/<id>` links and matching all use the stripped
name. The results CSV line for LEM is different: its Lab ID is the CDF's
sample name exactly as v1 wrote it, spaces and all (a missing or blank name
still falls back to the file name, as v2.0.0 said). This has been the
behaviour since v2.0.0, it is deliberate (the line must match v1's byte for
byte), and v5.1.0 does not change it. One consequence: a name ending in a
line break is stored as `40304` but still written to the CSV with the
break, and that is the name the new warning checks.

No schema change (the warning uses the existing review note); rolling back
to v5.0.1 is safe. A rolled-back hub keeps showing the note text as an
ordinary review note.
