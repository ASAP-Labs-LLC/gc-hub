**v5.1.0: a warning when LEM will misread a sample's Lab ID.**
Every result, report, results-CSV line and QBench upload is what v5.0.1
produced. The hub now tells you when a line it wrote to the results CSV
will be read wrongly by LEM; it does not change or hold back the line.

**Lab IDs with a comma or a line break**

- The results CSV line the hub writes for LEM quotes the Lab ID properly, as
  v1 did. LEM's reader does not honour the quotes: it splits each line at
  every comma and at every line break. So a sample named `40304, rerun`
  moves every later column one place to the right, and LEM silently records
  the wrong values for that row. A line break in the name (a carriage
  return, a new line, or one of the rarer characters Python treats as a line
  boundary: `\v`, `\f`, `\x1c`, `\x1d`, `\x1e`, `\x85`, ` `, ` `)
  splits the row and can make LEM record a fake one.
- When the hub writes such a row, it still writes it, byte for byte as
  before, and:
  - **marks the sample for review.** The Samples list shows the note on the
    row (shortened; hover for all of it), and the sample's header shows it
    in full, for example: *Review: Lab ID '40304, rerun' contains a comma;
    LEM will read this row's values one column off. Rename the sample in
    QBench/LEM by hand.* The classic page shows it as the sample's Review
    badge, as it does for a late blank.
  - **raises one notification**, for example: *Sample 412 on GC-1: Lab ID
    '40304, rerun' contains a comma; LEM will read this row's values one
    column off. Rename the sample in QBench/LEM by hand.* Its "Go to" link
    opens the sample.
- The note names what the Lab ID contains: "a comma", "3 commas" (three
  columns off), "a line break (\n)", or both. Line breaks are always shown
  escaped (`\r`, `\n`, ` `, ...), never as a real line break, and a
  very long name is shortened.
- **When it is checked:** whenever the hub writes a results-CSV row: a new
  result, a Re-process, Export to LIMS and a backfill release. A sample is
  notified once; exporting or re-processing it again adds the row as usual
  but no second notification. A late-blank note and the LEM note are kept
  side by side, and a Re-process with the current blank clears only the
  late-blank part.
- **Not checked:** results imported from v1's CSV (they write no row to the
  results CSV), and rows written before v5.1.0. A sample exported earlier
  is flagged the next time it is exported.
- The hub cannot rename a sample: the fix is to correct the sample name in
  QBench and the value in LEM by hand.

**Correction to the v2.0.0 notes**

The v2.0.0 notes said "The lab ID is the CDF's sample name with outer
whitespace stripped." That is true inside the hub: the stored Lab ID, the
Samples page, search, `/lab/<id>` links and matching all use the stripped
name. The results CSV line for LEM is different: its Lab ID is the CDF's
sample name exactly as v1 wrote it, spaces and all (a missing or blank name
still falls back to the file name, as v2.0.0 said). This has been the
behaviour since v2.0.0, it is deliberate (the line must match v1's byte for
byte), and v5.1.0 does not change it. One consequence: a name ending in a
line break is stored as `40304` but still written to the CSV with the
break, and that is the name the new warning checks.

No schema change (the note uses the existing review note); rolling back to
v5.0.1 is safe. A rolled-back hub keeps showing the note text as an
ordinary review note.
