**v2.0.0: the GC hub.** The app on ASAPSV1 stops watching a folder and becomes
the hub: CDFs are received (from the GC-PC agents, or loaded from a folder by
an admin), stored with every result in a database, processed per instrument,
and each final result is appended to the instrument's results CSV, the file
LEM tails. **Some numbers change** for the reasons listed below; each one is
something v1 did by accident or silently. Read this before installing, and
run the parity report (`tools/parity_report.py`) on a copy of GC-1's history
before the GC PCs are cut over: it must show no `unexplained` difference.

The copies on the share keep running v1.x until each GC PC is cut over. v2
does not run there (see DEPLOY.md, "Updating the share copies").

## Changes to results

- **Blank subtraction: the blank injected at or before the sample.** v1
  subtracted the latest blank it had *processed*, so the blank depended on the
  order files happened to arrive in. The hub uses the latest genuine blank on
  the same instrument, run with the same D2887 method, **injected at or
  before** the sample. A blank that arrives late (injected before samples
  already final) flags those samples for review and raises a notification;
  they are not reprocessed automatically. Reprocessing keeps the blank a
  result was computed with unless the operator asks for the current one.
- **Wider blank names.** A genuine blank is a sample whose name is a blank
  name *and* whose chromatogram passes the plausibility check. The names are
  now `Blank`, `blank2`, `blank_3`, `(Blank)` and `[b] Blank` (any case); v1
  recognised only the first three, so it treated `(Blank)` and `[b] Blank`
  runs as samples and blank-subtracted them.
- **Blank-named samples are never blank-subtracted** (as in v1), whether or
  not they pass the plausibility check.
- **A rejected blank is recorded.** When the blank carries too much signal for
  a sample (the relative-height guard), the sample is computed with **no**
  blank, as v1's numbers were, never with an earlier blank; the result
  records which blank was rejected and why.
- **Calibration auto-detection is off.** v1 silently fell back to
  auto-detected calibration peaks when fewer than two peak assignments were
  usable, which could label peaks with the wrong carbon numbers. The hub
  never guesses: an instrument whose calibration is unusable holds its
  samples as `awaiting_calibration` (with the reason) until the calibration
  is fixed, then processes them.
- **Stricter corrections, owned by the hub.** v1 read the correction factors
  file on every sample and used zero corrections, silently, when the file was
  missing, unreadable or malformed. The hub keeps each instrument's 11 D86
  correction factors in its own database (GC-1 is seeded once, at the first
  start, from the same file; a notification says so), records the values used
  on every result, and never applies a silent zero: without a complete set,
  samples wait as `pending_corrections`. **Never also enter GC factors in
  LEM**, which would apply them twice.
- **Injection-time parse fix.** v1 misread some ChemStation stamps
  (`20260925002450+0000` became 02:45:00 instead of 00:24:50; about 21% of
  GC-1's history has the tell-tale `:00` seconds). The hub parses the compact
  stamp first. This changes `InjectionDateTime`, ordering and duplicate
  detection, not the D2887/D86 values. The results table shows the corrected
  time for every sample, including imported v1 results, whose stored record
  keeps v1's original text.
- **Other methods are not processed.** Runs whose ChemStation method is not
  mapped to D2887 on the instrument (e.g. D7096 gasoline runs on a D2887 GC)
  are stored as `other_method` and never get D2887 numbers; a run with no
  method name is held for review. v1 processed every CDF as D2887.
- **Lab ID fallback.** The lab ID is the CDF's sample name with outer
  whitespace stripped. A blank or whitespace-only name falls back to the
  sender's file name (the agent's `X-GC-Filename`, or the loaded file's
  name) without its extension, then `Unknown`. v1 used the file stem only
  when the name was missing, and kept a whitespace-only name verbatim.
- **Conflicts are held, not overwritten.** A CDF with the same instrument,
  lab ID and injection time as an existing sample but different content is
  held as a conflict for an admin to keep or replace (Instruments page);
  it never replaces a result silently. An identical file is a duplicate and
  is ignored.
- **`GC_CAL_CDF` is ignored.** The calibration is each instrument's own
  (Calibration page); the environment override v1 honoured plays no part.
- **Corrections file edits after seeding are ignored.** GC-1's factors are
  read from `correction_factors.json` once, at the first start (retried
  every 10 minutes if the file is unreachable then). Later edits to that
  file change nothing; change the factors on the Instruments page.
- **Truncated CDFs are refused.** A CDF shorter than its header says, or with
  no intensity data, is rejected on receipt; v1 read the missing data as
  zeros and reported numbers for it.
- **QBench PDFs use the full analysis.** The report attached to a QBench
  sample is now built exactly like the exported analysis report: both
  deviation channels (the trend and the narrow-spike channel, which catches
  short tall spikes such as gasoline adulteration that the trend erases), the
  saved range overlays, and the calibration the result was computed with. v1
  used the trend channel only.

## Changes to how results are recorded and exported

- **Append-only exports.** Each result that becomes final (processed,
  released, reprocessed, or Export to LIMS) is appended once, in order, to the
  instrument's results CSV; bytes already written are never rewritten, so
  LEM's read position stays valid. GC-1 writes
  `data\results\gc1_results.csv` until an admin points it at the share CSV
  LEM tails and **adopts** it (Hub admin > Exports). A file changed behind the
  hub's back is refused, with a notification, until it is adopted again or
  moved. The `Source File` column holds the hub's own path to the stored CDF.
- **Revisions.** Reprocessing or re-exporting creates a new revision; earlier
  ones are kept.
- **Backfill is never exported automatically.** Samples injected before an
  instrument went live (GC-1: the first v2 start) are processed but reach the
  export and QBench only when an admin releases them.

## Operators and admins

- **Admin password.** There is no default password. At the first start the
  hub writes a one-time setup code to `data\admin-setup-code.txt` (and
  `app.log`); set the password at `/admin/setup`. Every admin action needs
  it, including saving the calibration page.
- **Samples are addressed by ID**, not by file path; the Scan & Parse, Stop
  Scan and Rebuild DB controls are gone (there is no folder to scan).
  Non-final samples show why they are held.
- **Settings**: only the flag rules and series colours can be changed from
  the browser, and the best-fit settings with the admin password; paths, the
  calibration, the corrections file and the blank limit are read-only there.
  Comparison standards are added from a sample, and adding, renaming or
  deleting one needs the admin password. The server-side Browse and Open
  Folder buttons are gone.
- **Hub admin page** (`/admin/hub`): load CDFs from a folder (one-shot,
  read-only on the folder, resumable) and the export actions (adopt, new path,
  write a fresh file).
- The hub backs up its database nightly (`data\backups\`, 14 kept).
- **`GC_DATA_DIR` is required**; the app exits with a message without it.
