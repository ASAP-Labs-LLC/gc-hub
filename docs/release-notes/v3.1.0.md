**v3.1.0: errors you can read, and two display fixes.** No D2887/D86 number
is calculated or stored differently. The results CSV, Export to LIMS and the
reports are unchanged, and none of them was ever affected by the two display
bugs below.

## Fixes

- **No more "Unexpected token '<'".** When the hub failed on an `/api/`
  request it could answer with a web page, and the browser showed
  `SyntaxError: Unexpected token '<', "<!DOCTYPE "... is not valid JSON`.
  This happened once on the admin setup page. Every `/api/` failure now
  answers with data. An unexpected error says *"Something went wrong on the
  hub (ref XXXX). Send the diagnostics bundle or app.log to have it looked
  at."*, and the same ref is written to `app.log` with the details. If a page
  still arrives where data was expected, for example from Cloudflare, the
  message says so: *"The hub answered HTTP 403 with a web page instead of data
  (Cloudflare: …)."*
- **Admin setup and password changes leave a trail.** Every attempt writes
  one line to `app.log`: the outcome, which check refused it, and how the
  request arrived (LAN or Cloudflare, https or not). It also records the new
  password's length as a range (under 12, 12–19, or 20 and over) and what
  kinds of characters it had (for example "length 12-19, non-ASCII: no"),
  never the password itself, and nothing at all about the current password. If an attempt leaves no line at all, it never
  reached the hub. Setup and password changes are tested with passwords
  containing `" ' < > & % \ / ; --`, `é`, `💥`, spaces, tabs and 128
  characters, over the LAN and through gc.asaplabs.net.
- **Sign-in through Cloudflare without https** now says *"Sign in over https:
  open https://gc.asaplabs.net"* instead of "Cross-site request refused".
- **Distillation Data table: the column headers were swapped.** The page
  labelled the D86 columns first and the D2887 columns second, but the data
  is in the results-CSV order (D2887 first). Every "D86 …" header therefore
  sat over a D2887 value, and every "2887 …" header over a D86 value. This
  goes back to the first version of the page. The header is now built from
  the data's own columns. The data itself was always right: the CSV, LIMS and
  reports use the correct columns.
- **Dashboard D86 table: 40% and 60% are shown.** The table always showed
  "—" at 40% and 60%, although every result stores them. ASTM D86 Appendix X4
  has no equation for them, so the hub stores the midpoint of the uncorrected
  30%/50% and 50%/70% values, and no correction factor applies to them. With
  **Corrected D86** ticked, the table shows the stored corrected values, except
  at 40% and 60%, which are those uncorrected midpoints in both modes; their
  tooltip says so. Unticked, it shows the stored values from before the
  correction factors. For results imported from v1, which have no stored
  uncorrected values, it converts the stored D2887 values and fills 40% and
  60% with the same midpoint rule, giving the numbers the hub would have
  calculated; those tables used to show only "—". A cell with no value shows
  "—" and a tooltip saying why.

## Live updates

The main page and the Instruments page now update themselves. Nothing needs a
page refresh any more:

- **New samples appear in the list as the GC PCs send them.** When a sample
  is processed, held, fails, is reprocessed, is exported to the results CSV
  or is uploaded to QBench, its row changes in place. The list keeps its
  scroll position and your selection.
- **The Refresh button and its Ctrl+R shortcut are gone.** Ctrl+R now just
  reloads the page, as in any browser.
- **The notification bell updates when a notification arrives,** not on a
  30-second timer.
- **The Re-process progress box follows the samples as they finish,**
  instead of asking the hub every 1.5 seconds.
- **On the Instruments page, an agent's status updates at each heartbeat.**
  "Last seen" counts up on screen ("12 s ago").
- **A small "Live · updated just now" line sits at the bottom left** of the
  main page. It changes to "Reconnecting… · last update 40 s ago" when the
  page can't reach the hub, and catches up on its own when the hub is back.
- **After the hub is updated, an open page says so:** "Updated to vX —
  reload to use it", with a Reload button. It never reloads by itself, so
  nothing you are in the middle of is lost.

The page asks the hub what changed every 3 seconds while the tab is visible,
and every 30 seconds while it's hidden. The hub answers from memory, so an
open tab doesn't slow processing. An open tab also doesn't count as someone
using the hub, including the rows it fetches after a change: the 3 AM
restart and the updater's idle deploy still happen with the page left open,
and a tab left open doesn't keep its sign-in alive.

After a hub restart or update, an open page reloads its list on its own.

Nothing about how results are calculated, recorded, exported or displayed
has changed.

For admins and developers: the new `GET /api/live?since=<cursor>` endpoint
(needs a signed-in session), `live.py` (the in-memory event ring) and
`static/js/live.js` (`window.GCLive`). `/api/files` also accepts
`ids=1,2,3`, which returns just those samples. A GET sent with the header
`X-GC-Background: 1` (what `GCLive.bgFetch` sends) is not counted as
activity.

## Sendable links

**Every sample now has a link you can send**, and other apps (COA Reviewer
first) can open a lab ID's GC result directly. Nothing about how results are
calculated or displayed changes.

- **By lab ID: `https://gc.asaplabs.net/lab/<lab ID>`**, e.g.
  `https://gc.asaplabs.net/lab/40329` or `…/lab/40318-RERUN-2`. It opens the
  hub with that lab ID's newest run selected: the latest injection, preferring
  final results, on any instrument. When the lab ID has several runs, the
  Dashboard lists the others ("Other runs of 40329: GC-2 · Sep 28 15:30") to
  switch to. The lab ID is matched exactly, else ignoring upper/lower case
  (A–Z only: accented letters must match exactly), and never as part of a
  longer ID. An unknown lab ID shows "No GC result for
  lab ID … yet" with a link to search.
- **By run: `https://gc.asaplabs.net/samples/<id>`** opens one exact run on
  the Dashboard; `…/samples/<id>/compare` opens it on the Analysis tab
  (`?standard=Diesel` also picks the comparison standard) and
  `…/samples/<id>/data` on Distillation Data, with its row highlighted.
- **Copy link**: right-click a sample (or use the **Copy link** button in the
  Dashboard's chromatogram header) to copy `https://gc.asaplabs.net/samples/<id>`,
  even when you opened the hub over the lab network (or the hub address is
  set to a lab-network name), so the link works for whoever receives it.
- **Links work when signed out**: the sign-in page opens first, then the
  linked sample.

For apps linking to the hub: build `https://gc.asaplabs.net/lab/` + the
URL-encoded lab ID (it is decoded once; a lab ID cannot contain `/`).
`GET /api/lab/<lab ID>` answers `{lab_id, sample_id, runs: [...]}` (or 404)
for a signed-in session. A "View in GC Hub" link inside COA Reviewer is a
separate COA change and is not part of this release.

## Setup guide and new Instruments pages

The first pages in the new design: monochrome and well spaced, with a light theme by default and a dark one in the user menu.

- **Instruments** (`/instruments`) shows one card per GC:
  - its LEM machine;
  - the agent's status: Live, last seen N min ago, or Never checked in;
  - samples today, held and waiting to export;
  - how far setup has got ("5 of 8 done · Next: Wait for the agent to check in", or "Ready"; the same words on every page, and "Setup · 5/8" in the sidebar).

  Below the cards, an Activity feed lists installer downloads, calibrations, correction factors, new runs and results written to the results CSV as they happen. **Add a GC** opens the setup guide.
- **One instrument** (`/instruments/<id>`) starts with a setup checklist while the GC is unfinished. After that come Agent, Calibration, Correction factors, Results file, Methods, Backfill and Conflicts. The actions are the same as before, and the agent's status updates without a refresh.
- **The setup guide** (`/setup`) takes a GC through eight steps in plain words: create it, enter the correction factors, install the agent, wait for the agent to check in, set the calibration, confirm the method, choose the results file and go live, then the first result.
  - Each step shows who did it and when.
  - A step moves on by itself when the agent checks in.
  - **Add a new GC** starts at step 1.
- **Going live asks for the results file first.** A GC is only "Ready" once its results go to the file LEM reads, or you have chosen on purpose to keep them in the hub's own file (LEM won't see those). Rows written to the hub's own file never reach LEM, even if you choose LEM's file later, so the guide asks before you go live. "Go live now" uses the hub's clock (or the GC's clock, once its agent has reported it), never your computer's, and warns first when the GC's clock is off. A start time in the future shows as "waiting until …".
- The Activity feed links each sample to its page and shows when it was injected. "Samples today" no longer counts imported history.
- Text and the focus outline meet the WCAG AA contrast level in both themes, and the version badge is easier to read.
- In the sidebar, the GC Hub mark goes to Samples (home). Settings and Help in the user menu open those windows on the Samples page.
- Admin changes still need the admin password. The page asks for it once and keeps it in the open tab for 15 minutes; it is never saved.
- The previous Instruments page is still at `/instruments/classic` for this release. The Calibration page keeps its layout but now uses the new colours and follows the chosen theme.
- **Database:** schema v4 adds `instrument_events`, which records who downloaded an installer, saved a calibration or correction factors, mapped a method, set the results file or `live_since`, or revoked a key. The change is additive: v3.0.0 still starts on a v4 database if you roll back.
- Instrument ids `activity`, `classic`, `new` and `setup` are reserved, because those words are used in page addresses.

## Purge instrument data

**Hub admin > Purge instrument data** removes one instrument's samples from
the hub, for example "purge GC-1's samples and keep GC-2 and the settings",
without anyone editing `gc.db` by hand.

- **Scope:** *all samples* of the instrument (and its conflicts), or
  *backfill only* (the imported history, to redo an import; live samples are
  kept).
- **What goes:** the samples and every row that belongs to them: results
  (revisions), export rows, the sample cache, conflicts, comments, report
  records and queued jobs, in one database transaction that either completes
  or changes nothing.
- **What stays:** the instrument and all its settings (calibration,
  corrections and their history, methods, LEM machine, live since, results
  file, agent and token), the other instruments' data, the global settings and
  the comment presets. A sample that something kept still points at (the blank
  a kept result subtracted, another instrument's conflict) is kept too.
- **Nothing is deleted from disk.** The whole database is first copied to
  `data\backups\pre-purge-<instrument>-<time>.db`, which the nightly clean-up
  never removes. The purged samples' CDFs are **moved** to
  `data\purged\<instrument>-<time>\`, with a list of every file; a CDF that is
  still in use (a calibration, one a kept result was computed with, a
  comparison standard, a kept result's blank) stays where it is.
- **The results CSV that LEM reads is not edited.** Rows already in it stay;
  if the same runs are sent again after the purge, they are appended again.
  The preview says how many purged samples were already in the file, and a
  new results file for the instrument can be set as part of the purge.
- **How:** choose the instrument and scope, *Preview* (counts, files, what is
  kept and why), type the confirmation shown (`PURGE <instrument name>`, with
  the instrument's id added when two instruments share a name), *Start*, and
  follow the progress (the page picks up a running or finished purge when it
  opens). It runs as an admin job (one at a time). While it runs, that
  instrument's processing pauses and its agent's uploads are answered "purge
  in progress; retry" (the agent waits and sends them again); the other
  instruments carry on. Operator actions on the purged instrument's samples
  are not paused and may act on samples that are about to be removed.
- **Safe against a crash:** a purge the hub stops in the middle of is
  abandoned (nothing changed, its backup deleted) or finished at the next
  start, with a notification either way. A problem after the data was
  removed (a file that could not be moved, a refused results file) makes it
  *completed with warnings*, listed on the page and in the notification.
- **Undo:** see DEPLOY.md, *Restore after a purge*. Restoring the backup rolls
  back **every** instrument to the backup's time.

## Restart waits for background work

A restart (Settings, "Restart & install", the hub tray) and the tray's Stop
now name any background work in progress (a folder load, a history import or
its dry run, a purge, a diagnostics bundle, a report ZIP, a QBench upload,
running processing jobs) and ask before interrupting it; a purge can never be
interrupted. The updater no longer installs an update while such work runs
(the hub reports itself busy). A history import interrupted anyway is marked
at the next start with a notification saying how far it got; pressing Start
again resumes it, and nothing is lost.
## Running now, the GC strip and Hub admin (v4.0 lane E)

- **"Running now"**: bottom-left on the main page, where "Ready" was. While
  work runs it names it and its progress ("Importing GC-2 history ·
  3,000/12,000"). Click it for the list, titled "Running now" while
  something runs and "Recent work" after: who started each task and when, and
  Open / Download / Dismiss (Dismiss keeps the list open). A finished task
  says what happened in one line with its count, e.g. "Re-processed 1
  sample", "GC-1 dry run finished · 40 classified", "Diagnostics ready ·
  12 MB". It covers folder loads, the v1 history import and its dry run,
  diagnostics bundles, report ZIPs, QBench uploads and re-process batches,
  whoever started them. A finished or failed task stays for 30 minutes, or
  until you dismiss it in your browser; an import a restart cut short shows as
  "interrupted by a restart". Only the person who built a report ZIP gets its
  Download.
- **GC strip**: one compact chip in the top bar, "2/2 GCs live" (glyph and
  text, never colour alone), updated on each check-in and ticking on its own
  between them; click it for each GC's status and a link to its page. A GC is
  live when its agent checked in within the last 90 seconds, on the hub's
  clock. Every page uses this one rule (the Instruments pages used 15 minutes
  and 150 seconds, by the browser's clock).
- **Toolbar**: Advanced Views, Comparison Export, Help and Restart Server
  moved under **More ▾**, so the top bar fits at 1366 px.
- **Processing paused**: a one-line banner on the main page while processing
  is paused, with who paused it, when, and how many runs are waiting.
- **Sample list**: rows sit under day headings (Today, Yesterday, "Thu 24
  Sep", on the hub's calendar, moving on at midnight) and show their injection
  time (the full date in the tooltip); runs whose CDF had no injection time
  come last under "No injection time". A switch above the list sorts by
  **Newest run** (the default) or **Lab ID** in number order (40318,
  40318-RERUN-2, 40319; accents ignored, blank IDs last), where each row shows
  its date and time; your browser remembers the choice. Lab IDs are shown in
  full, never cut to "4…".
- **Hub admin**:
  - Fixed: *Load CDFs from a folder* could never start (its instrument list
    was empty).
  - Fixed: the history import's progress showed in the folder-load card, and a
    dry run showed twice. Each job now shows in its own card: one line with
    when it finished ("Dry run finished at 14:05 · nothing written") and a
    short table of counts instead of raw JSON.
  - Unlock once with the admin password: "Unlocked" shows only after the hub
    accepts it, it is kept in the tab for 15 minutes, and sessions, presets,
    results files and diagnostics sizes load by themselves. The per-card Load
    and Refresh buttons are gone. A request that hangs is given up after
    30 s, and a job being followed is polled again after an error.
  - Running work shows as soon as the page opens, without the password, and a
    running job is picked up where it is.
  - Messages appear next to the button you pressed and clear when the job
    ends; Stop is enabled only while that card's job runs; one primary button
    per card.
  - Results files: New path and Write fresh take the path in a field under
    the row, not a browser prompt; long paths wrap without breaking words
    elsewhere.
  - Sections run from what you check most (running work, results files,
    imports) to one-time setup (hub address) last, with "← Back to GC Hub"
    at the top.
- **Settings and the standards menu** ask for the admin password in a masked
  dialog (kept for 15 minutes in the tab once the hub accepted it), never in a
  plain-text prompt.

For integrators: `GET /api/live` gains `tasks` (running tasks, and those that
ended in the last 30 minutes: `{id, kind, title, instrument, state,
