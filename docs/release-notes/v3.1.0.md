**v3.1.0: errors you can read, and two display fixes.** No D2887/D86 number
is calculated or stored differently. The results CSV, Export to LIMS and the
reports are unchanged, and none of them was ever affected by the two display
bugs below.

## Fixes

- **No more "Unexpected token '<'".** When the hub failed on an `/api/`
  request it could answer with a web page, and the browser showed
  `SyntaxError: Unexpected token '<', "<!DOCTYPE "... is not valid JSON`.
  This happened once on the admin setup page. Every `/api/` failure now
  answers with data. An unexpected error says *"Something went wrong on the
  hub (ref XXXX). Send the diagnostics bundle or app.log to have it looked
  at."*, and the same ref is written to `app.log` with the details. If a page
  still arrives where data was expected, for example from Cloudflare, the
  message says so: *"The hub answered HTTP 403 with a web page instead of data
  (Cloudflare: …)."*
- **Admin setup and password changes leave a trail.** Every attempt writes
  one line to `app.log`: the outcome, which check refused it, and how the
  request arrived (LAN or Cloudflare, https or not). It also records the new
  password's length as a range (under 12, 12–19, or 20 and over) and what
  kinds of characters it had (for example "length 12-19, non-ASCII: no"),
  never the password itself, and nothing at all about the current password. If an attempt leaves no line at all, it never
  reached the hub. Setup and password changes are tested with passwords
  containing `" ' < > & % \ / ; --`, `é`, `💥`, spaces, tabs and 128
  characters, over the LAN and through gc.asaplabs.net.
- **Sign-in through Cloudflare without https** now says *"Sign in over https:
  open https://gc.asaplabs.net"* instead of "Cross-site request refused".
- **Distillation Data table: the column headers were swapped.** The page
  labelled the D86 columns first and the D2887 columns second, but the data
  is in the results-CSV order (D2887 first). Every "D86 …" header therefore
  sat over a D2887 value, and every "2887 …" header over a D86 value. This
  goes back to the first version of the page. The header is now built from
  the data's own columns. The data itself was always right: the CSV, LIMS and
  reports use the correct columns.
- **Dashboard D86 table: 40% and 60% are shown.** The table always showed
  "—" at 40% and 60%, although every result stores them. ASTM D86 Appendix X4
  has no equation for them, so the hub stores the midpoint of the uncorrected
  30%/50% and 50%/70% values, and no correction factor applies to them. With
  **Corrected D86** ticked, the table shows the stored corrected values, except
  at 40% and 60%, which are those uncorrected midpoints in both modes; their
  tooltip says so. Unticked, it shows the stored values from before the
  correction factors. For results imported from v1, which have no stored
  uncorrected values, it converts the stored D2887 values and fills 40% and
  60% with the same midpoint rule, giving the numbers the hub would have
  calculated; those tables used to show only "—". A cell with no value shows
  "—" and a tooltip saying why.
