**v5.0.1: stability fixes found by testing v5.0.0 against v1 and against bad input.**
Every result, report, results-CSV line and QBench upload is what v5.0.0
produced. These are fixes for crashes, stalls and two ways the report queue
could send the wrong thing.

**Samples that used to crash now finish**

- A weak sample run after a blank with heavy column bleed could be wiped out
  completely by the blank subtraction, and the sample stopped in `error`. It
  is now processed without that blank, exactly as v1 did, and the sample
  notes say the blank was rejected.
- A file named like a blank whose time and signal arrays have different
  lengths, or a zero or NaN sampling interval, made the upload fail with a
  server error. The GC agent retries server errors forever, oldest file
  first, so one such file stopped everything behind it from that GC. It is
  now received as an ordinary sample. A malformed file is never taken as the
  reference blank (one could previously become the blank and break every
  later sample on that instrument).

**The hub no longer falls over on hostile or corrupt CDFs**

- A CDF claiming a tiny sampling interval, or a small netCDF-4 file
  declaring hundreds of millions of values, could exhaust memory and crash
  the hub. Because received samples are requeued at start, it crashed again
  on every restart. The first is capped with no change to any result; the
  second is refused at upload with a clear message.
- A complete NetCDF-3 file with a single byte or short record variable was
  wrongly refused as truncated.
- A file time from the agent outside 1971–2100 (a zeroed timestamp, for
  example) caused a server error. It is now ignored: a CDF with its own
  injection stamp is processed normally, and one without is refused with a
  message naming the file time it ignored.

**Server answers**

- A request body that is not a JSON object, a garbled live-update cursor,
  and several malformed fields no longer cause server errors; they get a
  clear 400. "Skip" on a QBench queue item no longer accepts a negative
  position (which marked the last item as skipped while still uploading it).
- While the database is busy (a long import or purge), requests answer
  "busy, try again" (503 with `Retry-After`) instead of a server error asking
  for the diagnostics bundle. Only a genuinely busy database does this.
- A very large "select all" list of sample ids no longer freezes every other
  request for 20 seconds.

**The redesigned pages**

- The live indicator now notices a hung hub: after 15 seconds without an
  answer it says "Not connected · retrying", and updates resume by themselves
  when the hub recovers. Before, it kept saying "Live · updated N min ago"
  and needed a page reload.
- Report queue: Upload can no longer be clicked twice while the upload is
  starting. If the hub is slow to answer, the sheet checks for itself
  whether the upload started, for up to a minute, instead of guessing. It
  matches running uploads to queued reports by sample, never by Lab ID, so a
  re-run of a Lab ID is never marked sent by mistake.
- Changing the filter while a live update is arriving no longer mixes rows
  from the old filter into the list. "All N matching" keeps its count
  current. Compare can no longer open twice. Going Back from a missing
  sample shows "Pick a sample" again.
- The sample panel's results table no longer slides under the version badge
  in the bottom-right corner (Mac trackpads hide the scrollbar that used to
  leave room). It reserves room for the badge's real width.

**Testing added**

- `tests/replay/`: a differential replay against the v1 production code.
  The same calibration, blank, corrections and about 70 generated samples
  go through v1 and the hub, and every results-CSV column must match
  string for string, apart from the changes listed in earlier release notes
  (for example the v2.0.0 injection-time fix, now checked against known
  times). CI runs it against a recording of v1's output; with the share
  snapshot present it runs v1 itself and the real calibration and blank
  CDFs. It also reproduces all 80 production rows of v1's results CSV.

**Documented, unchanged since v2.0.0:** a D86 correction factor beyond
±50 °C is refused (`corrections.MAX_ABS_CORRECTION_C`); earlier notes did
not say so.

No schema change; rolling back to v5.0.0 is safe.
