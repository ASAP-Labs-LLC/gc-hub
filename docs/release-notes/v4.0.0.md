**v4.0.0: the hub updates live, a step-by-step guide for setting up a GC, sendable sample links, purging a GC's data, and the first pages of the new design.** This is a MAJOR release because two display fixes change what analysts see (below). No D2887/D86 number is calculated, stored or exported differently. The results CSV LEM reads, Export to LIMS and the report PDFs are unchanged.

## Upgrading from v3.0.1

- **Installing:** use Settings > "Restart & install v4.0.0" as usual. Restart now waits for background work (see *Restart waits for background work* below), so finish or let any import finish first.
- **Database:** the store migrates from schema v3 to v4 at the first start. It adds one table, `instrument_events`, and changes nothing that exists. A copy is written first to `data\backups\pre-migrate-3-<time>.db`.
- **Rolling back to v3.0.1 is safe.** It starts on the v4 database and ignores the new table. Nothing entered in v4 is lost; it reappears after upgrading again.
- **No agent reinstall.** The GC PC agents need no change. The hub tray is updated with the release.
- **Everyone keeps their sign-in.** Sessions survive the update.

## Display fixes (why this is v4)

- **Distillation Data table: the column headers were swapped.** The page labelled the D86 columns first and the D2887 columns second, but the data is in results-CSV order (D2887 first). So every "D86 …" header sat over a D2887 value and every "2887 …" header over a D86 value. This goes back to the first version of the page, and the data itself was always right. The header is now built from the data's own columns.
- **Dashboard D86 table: 40% and 60% are shown.** They always showed "—", although every result stores them. ASTM D86 Appendix X4 has no equation for 40% or 60%, so the hub stores the midpoint of the uncorrected 30/50% and 50/70% values; no correction factor applies to them, and their tooltip says so. With **Corrected D86** unticked, the table shows the stored values from before the correction factors. For results imported from v1, which have no stored uncorrected values, it converts the stored D2887 values instead, giving the numbers the hub would have calculated.

## Live updates: no more refreshing

- **The sample list updates as runs arrive.** New samples appear as the GC PCs send them, and a row changes in place when its sample is processed, held, fails, is re-processed, is written to the results CSV or is uploaded to QBench. The list keeps its scroll position and your selection.
- **What else updates live:**
  - the notification bell;
  - the Re-process progress;
  - agent status everywhere, including "last seen", which counts up on screen.

  The Refresh button is gone.
- **"Live · updated just now"** sits at the bottom left, and changes to "Reconnecting…" when the hub can't be reached.
- **After an update, an open page offers a Reload button.** It never reloads by itself.
- **An open tab doesn't count as someone using the hub,** so the 3 AM restart and idle updates still happen, and a forgotten tab doesn't keep its sign-in alive.

## Running now and GC status, on every page

- **"Running now"** names background work and its progress, e.g. "Importing GC-2 history · 3,000/12,000". It covers folder loads, the v1 history import and its dry run, purges, diagnostics bundles, report ZIPs, QBench uploads and re-process batches, whoever started them.
  - Click it for the list: Open, Download (only for your own report ZIP) and Dismiss.
  - A finished task says what happened in one line, e.g. "GC-1 dry run finished · 40 classified", and stays for 30 minutes.
  - Work a restart cut short shows as "interrupted by a restart".
- **GC status:** "2 of 2 GCs live" in the top bar and the sidebar. Click it to see each GC's status, with a link to its page.
  - A GC is live when its agent checked in within the last 90 seconds, by the hub's clock. The same rule is used everywhere.
  - Status shows as a symbol and a word, never colour alone.
- **Processing paused:** a one-line banner on every page while processing is paused, saying who paused it, when, and how many runs are waiting.

## The new design, the setup guide and Instruments

These are the first pages in the new design: monochrome, well spaced, light by default, with a dark theme in the user menu. Every page has a sidebar, so every page has a way home.

- **Instruments** (`/instruments`) shows a card per GC with:
  - its LEM machine and agent status;
  - samples today, held and waiting to export;
  - its setup progress ("5 of 8 done · Next: Wait for the agent to check in", or "Ready").

  Below the cards, a live Activity feed lists installer downloads, calibrations, correction factors, new runs and results written to the CSV.
- **Each GC** (`/instruments/<id>`) starts with its setup checklist while the GC is unfinished. After that come Agent, Calibration, Correction factors, Results file, Methods, Backfill and Conflicts.
- **The setup guide** (`/setup`) takes a new GC through eight steps in plain words:
  1. Create it and pick its LEM machine.
  2. Enter the 11 correction factors.
  3. Install the agent on the GC's computer.
  4. Wait for the agent to check in.
  5. Set the calibration.
  6. Confirm the method.
  7. Choose the results file and go live.
  8. See the first result.

  Each step shows who did it and when, and moves on by itself.
  - **Going live asks for the results file first.** Rows written to the hub's own file never reach LEM, so a GC only counts as "Ready" once its results go to the file LEM reads, or you chose on purpose to keep them hub-only.
  - "Go live now" uses the hub's clock (or the GC's), never your computer's.
- **Hub admin and Calibration** now sit in the same layout.
  - Hub admin has a section list that follows you as you scroll, ordered by how often you use each part, from running work down to one-time setup (the hub address).
  - A new read-only **Server** section shows the version, a pending update, uptime, whether processing is paused and by whom, the queue and memory. Pause, resume and stop stay on the tray.
  - Calibration no longer has its own password box.
- **The same admin unlock everywhere.** Every page asks for the admin password with the same dialog, then keeps it for 15 minutes while you stay on that page. It lives in the open tab only and is never saved, so moving to another page asks once more. Settings no longer asks for it in a plain-text box.
- **The sample list:**
  - rows sit under day headings (Today, Yesterday, then the date) and show their injection time;
  - a switch sorts by **Newest run** (the default) or **Lab ID** in number order (40318, 40318-RERUN-2, 40319);
  - runs with no readable injection time come last;
  - lab IDs are shown in full.
- **The top bar fits at 1366 px.** Help, Restart Server, Advanced Views and Comparison Export moved under **More ▾**.
- **Contrast:** text and the keyboard focus outline meet WCAG AA in both themes.
- **The sidebar's Setup guide item names the GC**, e.g. "GC-2 · 5/8", so one unfinished GC can't hide another's progress.
- **A notification is no longer added again** while the same one is still unread.
- **The old Instruments page** is still at `/instruments/classic` for this release.

## Sendable links

- **`https://gc.asaplabs.net/lab/<lab ID>`** opens that lab ID's newest run (preferring final results, on any GC) and lists its other runs. COA Reviewer and other apps can link here. A lab ID can't contain `/`.
- **`https://gc.asaplabs.net/samples/<id>`** opens one exact run. `/compare` opens it on Analysis (`?standard=Diesel` picks the standard) and `/data` on Distillation Data with its row highlighted.
- **Copy link** (right-click a sample, or the button on the Dashboard) always copies the gc.asaplabs.net address, so the link works for whoever receives it.
- **Signed-out visitors** sign in first, then land on the sample.
- **Fixed:** opening a sample picks its best-fit standard and now actually shows it selected and runs the comparison.

## Purge instrument data

**Hub admin > Purge instrument data** removes one GC's samples from the hub, for example "purge GC-1 and keep GC-2 and the settings", without anyone editing the database by hand.

- **Scope:** all of the GC's samples, or only its imported history (to redo an import).
- **Kept:**
  - the GC itself and all its settings: calibration, correction factors, methods, LEM machine, results file, agent and key;
  - the other GCs' data;
  - global settings;
  - any file something still uses.
- **Nothing is deleted from disk.**
  - The database is copied first to `data\backups\pre-purge-<GC>-<time>.db`, which the nightly clean-up never removes.
  - The purged samples' CDFs are moved to `data\purged\<GC>-<time>\`.
- **The results CSV LEM reads is not edited.** If the same runs are sent again, they are appended again. The preview says how many were already in the file, and you can start a new results file as part of the purge.
- **How it runs:**
  1. Preview.
  2. Type the confirmation shown, e.g. `PURGE GC-1`.
  3. Start and follow its progress.

  Only that GC pauses while it runs, and its agent resends afterwards.
- **Safe against a crash:** an interrupted purge is either abandoned (nothing changed) or finished at the next start, with a notification.
- **Undo:** see DEPLOY.md, *Restore after a purge*. Restoring rolls back every GC to the backup's time.

## Restart waits for background work

- **Restart and Stop now ask before interrupting work.** This covers Settings' Restart, "Restart & install" and the tray's Restart. If background work is running (an import or dry run, a folder load, a purge, a diagnostics bundle, a report ZIP, a QBench upload, or running processing jobs), they name it and ask before interrupting it. The tray's Stop already asked in v3.0.1.
- **A purge can never be interrupted.**
- **Updates wait too:** the updater doesn't install an update while such work runs.
- **An interrupted import resumes.** If an import is interrupted anyway, the next start says how far it got, e.g. "press Start to resume; nothing was lost".

## Errors you can read

- **No more "Unexpected token '<'".** Every failed request now shows a readable message. An unexpected error gives a reference, e.g. "ref 7F3A", that matches a line in `app.log`. If Cloudflare answered instead of the hub, the message says so.
- **Setup and password changes leave a trail in `app.log`.** It records the outcome, which check refused it, and whether the request came over the LAN or through Cloudflare. It never records the password, only a rough length and which kinds of characters it had.
- **Sign-in over plain http through Cloudflare** now says "Sign in over https: open https://gc.asaplabs.net".

## For integrators

- **`GET /api/live?since=<cursor>`** (signed-in session) returns what changed: `samples`, `instruments`, `agents` (with `name`, `live` and `last_seen_age_s`), `tasks`, `notifications_unread`, `hub` (with `processing_paused`, `queue` and `exports_pending`), `version`, `server_now` and `server_today`.
  - `tasks` never carries paths, tokens, parameters or error text.
  - A GET with `X-GC-Background: 1` is not counted as activity.
- **`/api/files`** accepts `ids=1,2,3`.
- **`GET /api/agents`** gains `live` and `last_seen_age_s`.
- **`GET /api/lab/<lab ID>`** returns `{lab_id, sample_id, runs}` or 404.
- **`GET /api/instruments/<id>/setup`** returns the eight steps.
- **`GET /api/instruments/activity`** returns the Activity feed.
- **Every `/api/` error** answers JSON `{error, status, ref}`.
