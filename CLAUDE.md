# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The **GC hub** (v2): one Flask process on ASAPSV1 that receives gas-chromatograph `.CDF` files (from the GC-PC agents over HTTP, or an admin folder load), stores them and their results in SQLite, runs an ASTM D2887 simulated distillation and derives ASTM D86 temperatures per instrument, appends each final result to the instrument's results CSV (the file LEM tails), serves Plotly traces and the results table, and can attach generated PDF reports to QBench samples. It began as a 1:1 web clone of the PyQt5 desktop "GC Viewer & Distillation Parser" (documented in the `gc-data` repo); the UI still looks like it (the redesign is phase 5). Phase 2 design: `docs/superpowers/specs/2026-09-28-phase2-multi-instrument-hub-design.md`; phases 3+4 (range-driven deviation bullets, comments, `report_log`; v3.0.0): `docs/superpowers/specs/2026-09-29-phase3-4-bullets-comments-design.md`.

## Deployment topology (important, not obvious from the code)

- **Production is ASAPSV1 under the COA Reviewer updater**: a `v*` tag builds a release, the updater installs it into `C:\ASAPApps\gc\releases\<tag>\`, health-checks it and runs it on port 5560 with all state in `C:\ASAPApps\gc\data\` (`GC_DATA_DIR`). See *Deployment* below, `RELEASING.md` and `DEPLOY.md`.
- **v2 is hub mode only (spec D14).** `app.py` refuses to start without `GC_DATA_DIR`; `run.pyw`, `looker.py`, the watch-folder scanner and the per-port instances are gone. The copies on `\\ASAPServer\Labsharedrive` (launched by `run.pyw` on the GC workstations) keep running **v1.x** until each GC PC is cut over to the agent. Share fixes come from branch **`maint/v1`** (cut at v1.1.0) and are hand-copied per DEPLOY.md; they are **never published as GitHub releases** (the updater follows "latest", so a later v1.x release would downgrade ASAPSV1; a v1.x tag only with `make_latest=false`).
- **Development is on a Mac**, in this git checkout (`~/Projects/gc-hub`). Do not edit the share copies to ship a change; tag a release.
- **Windows-isms are intentional, not bugs:** `chromedriver.exe`, UNC credential paths (`\\ASAPServer\...\qbenchlogin.txt`), `os.environ["TEMP"]`, `msvcrt` locks in `exports.py`, `taskkill`/`CREATE_NEW_PROCESS_GROUP` in the restart code. Don't "port" them to POSIX.
- **History:** the share folder this code came from is `GC 2026.5 2887 Advanced analysis/`. `GC 2027/webapp` is the 2026-06-16 build with D7096 *gasoline* modules bolted on (the gasoline fork, not newer diesel work).

## Run / develop

```bash
# from the repo root
pip install -r requirements.txt -r requirements-dev.txt   # Python 3.12+ (numpy/scipy pins require it)
GC_DATA_DIR=/tmp/gcdata python app.py              # http://0.0.0.0:5560, debugger off
GC_DATA_DIR=/tmp/gcdata python app.py --dev        # Flask debug mode (interactive debugger: never in production)
GC_DATA_DIR=/tmp/gcdata PORT=5570 python app.py    # as the updater runs it (PORT wins; else --port, GC_PORT, 5560)
```
Without `GC_DATA_DIR` the app exits with code 2 and a message pointing to DEPLOY.md. `app.py` accepts `--port`, `--dev` and `--no-tray` (ignored; the updater's `health_args`). Any other flag is an error, and prefixes are not expanded (`--d` is not `--dev`). The first start in a data folder creates `gc.db`, the `gc1` instrument (from `settings.json`), gc1's corrections (seeded once from `correction_factors_json`) and `admin-setup-code.txt`; set the admin password at `/admin/setup`. Server-side tools: `python tools/load_folder.py`, `python tools/parity_report.py`, `python tools/import_history.py` (dry run only); the parity runbook is in DEPLOY.md ("Parity check before cutover"): the loader runs on a **scratch** data folder with `--copy-instrument-from <production data>` (production's `gc.db` read-only; copies the instrument's calibration CDF + assignments, method map, `live_since` and hub corrections, plus `settings.json` and comparison standards, never the export path or token) and `--process`, which refuses only a folder a hub has served (`app.log` in it) unless `--hub-port` names that hub's port and nothing answers there.

## Deployment

- **Every piece of state lives under `GC_DATA_DIR`** (`paths.py`): `gc.db` (+ `backups/gc-<date>.db`, 14 kept), `cdf/<inst>/<YYYY>/<MM>/…` (raw CDFs, kept forever), `results/<inst>_results.csv` + `.gchub.json` sidecar (unless an instrument's `export_path` points at the share CSV LEM tails), `settings.json`, `exports/` (report PDFs), `gc_comparison_standards/`, `notifications.json`, `admin-setup-code.txt` (until setup), rotating `app.log`. `PORT` wins over every other port source, there is no pidfile, and a restart only **exits** so the updater relaunches it (except while the updater is `paused`, when it spawns its own replacement).
- **`GET /healthz`** is the updater's contract: HTTP 200 with `{status: "ok", version, pid, active_sessions, idle_seconds}`. `version` is the `VERSION` file (`version.py`; `"dev"` in a checkout), and must equal the release tag. No auth, no outbound calls, and polling it does not count as activity. It also carries `hub` (`hub_control.status_snapshot()`, never part of the contract), served from a cache refreshed off the request path, so `/healthz` never waits on SQLite. Through the Cloudflare tunnel it answers only `{status, version, pid}`. The health check boots the app with an **empty** `GC_DATA_DIR`: the hub starts on a background thread (store, gc1, Worker, exporter) and `/healthz` answers at once; no calibration or corrections → samples would wait, which is fine. `tests/test_healthz.py` boots it exactly that way.
- **Restart installs a staged update.** `POST /api/restart` asks `restart_policy.decide()` whether the updater has a newer healthy release staged; if so it writes `switch-requested` and waits for the updater's `switch-accepted`/`switch-refused` (`restart_update.py`, the handshake), falling back to a plain restart. The Restart button (Admin · Server since v5.0, `admin_restart.js`; the classic Settings modal too) reads "Restart & install vX.Y.Z" when a release is staged. The hub's threads are stopped right before the process exits (`_stop_hub`; when the updater accepts a switch, `on_taken=_stop_hub`), and started again if a self-respawn fails.
- **Never edit a release folder** on the server; releases are immutable. Ship by tagging: `git tag -a vX.Y.Z -m "..." && git push origin vX.Y.Z` (commit pushed first). `.github/workflows/release.yml` runs `.github/workflows/ci.yml` (also on every push: both suites on Python 3.12 and 3.14 with `GC_REQUIRE_DEPS=1`, identity checks against coa-reviewer's latest release, an advisory Windows install + boot), `exports-ci.yml` and `agent-ci.yml`, then a separate write-token job runs `scripts/package_release.sh`, the single source of truth for the zip's contents (tracked source only; state excluded by name; `VERSION` stamped from the tag; tags must be `vX.Y.Z[-pre]`; a tag containing `-` is published as a prerelease, which the updater never stages; `docs/release-notes/<tag>.md`, when present, heads the release notes). Anything that changes how results are calculated, recorded or displayed is a MAJOR bump. See `RELEASING.md`; first-time server setup is in `DEPLOY.md`.
- **`requirements.txt` pins everything with `==`**, transitive deps included (frozen from a Python 3.14 venv; platform-only packages carry markers). The hub process never imports `pystray`/`PIL`/`watchdog`; `pystray` is pinned (Windows only) for the hub tray, which runs with the release's `.venv`, and `psutil` for the process CPU/RSS in the status (the agent declares its own deps in `agent/requirements-agent.txt`). The updater builds each release's venv from it with its own Python on Windows, recorded as CPython 3.14.4; see `RELEASING.md` "Dependency pins".
- **`supervisor.py` and `restart_update.py` are byte-identical copies of coa-reviewer's** (the updater imports whichever app's copy it finds first). Never edit them here; change them in coa-reviewer and copy. `tests/test_restart_update.py` checks when `../coa-reviewer` exists (CI clones its latest release there).

## Architecture

- **`app.py`** — the Flask app and its routes; samples are addressed by `sample_id` and every route reads the store (route fates: `docs/superpowers/plans/2026-09-28-phase2-T4-routes.md`, pinned by `tests/test_route_fates.py`). It refuses to start without `GC_DATA_DIR`. `_init_app()` starts the hub on a background thread (`hub.start_with_retry(hub.start)`: 5 s doubling to 5 min, notified after 3 failures; then primes `sample_cache`) and the 3 AM auto-restart loop (idle = no requests, no QBench upload, no running admin job, no due Worker job); it runs on import, and under `__main__` after the port guard (`supervisor.wait_until_free`; a second bind to a served port succeeds silently on Windows) and the tidy-up of switch files. **Importing `app` therefore has side effects** — tests assert the route surface via AST instead of importing it. Reports, the dashboard numbers, `/api/table` and Export to LIMS read the **stored revision** and never recompute (`/api/table` shows the sample's corrected `injection_dt`, other cells as stored). `/api/settings` POST (JSON only) changes only `settings.OPERATOR_KEYS` (flag rules, series colours) and, with the admin password, `settings.ADMIN_KEYS` (`bestfit_*`, `analysis_*`); any other changed key is a 400 (paths, calibration, corrections, `blank_max_intensity_pa`), and the standards and export folders are fixed under the data folder. Comparison standards are added from a `sample_id` only; add/rename/delete are admin-gated. `POST /api/calibration` is admin-gated. There are no server-side desktop actions (`/api/browse`, `/api/open-folder` are gone). QBench uploads run in a background thread and stream progress over **Server-Sent Events** (`/api/qbench-upload/stream`, a keep-alive comment every 0.5 s); each PDF is built with `_build_report_pdf`, like the direct and ZIP exports. **Nothing that can take minutes runs in a request** (v3.0.1): through gc.asaplabs.net Cloudflare ends a request after 100 s with HTTP 524, so such work answers 202 `{job}` and is polled (`tests/test_route_fates.py` `LONG_WORK`). The report ZIP (`POST /api/export-analysis-reports-zip`, about 2.5 s per PDF) is built by `download_jobs.DownloadJobs` (`REPORT_ZIPS`: a thread per build, at most 2 at once, the owner's signed-in name only, `GET …/<job_id>` to poll, `GET …/<job_id>/download` once, then deleted; 10 minutes; `<data>/report-zips-tmp`, cleared at start-up); a build or a waiting ZIP holds off the 3 AM restart and the tray's Stop. **`_report_content(sample, params, conf, db)` is the one analysis pass** behind `/api/analysis` and every export (`items`, `text`, `conclusion_generated`, `windows`, `params_used`, `comments`, …) and the PDF's only analysis input; `_report_request` takes the report fields from a body/queue item (a client `bullets` string is never read). The report HTML escapes every interpolated string and its footer prints the parameters, ranges and app version; its Comments section prints `text (initials, date)`, or `text (Cx–Cy, a–b min; initials, date)` for an annotation, carbons from the report's ladder (`_comment_line`). Comments and `report_log` rows go through phase 4's `comments` module (a hard import: `comments.for_report`, `comments.log_report`, one row per PDF). Carbon labels always come from the sample's own revision (`_revision_ladder`: its `calibration_used` anchors, else its instrument's `distill.calibration_ladder`), never gc1's: `/api/analysis` returns `cal_times`/`cal_carbons`, and so does `GET /api/samples/<id>/trace` (for the current or `?revision=` revision), which the page's carbon markers use; the main page does not read `GET /api/calibration`. The upload queue is append-while-running and supports mid-run credential re-prompt and per-item skip.
- **`hub.py`** — the one start-up (`hub.start(app_conf)` → `HubRuntime`; `running()`, `.stop()`, `.wake_exports()`; `start_with_retry`; `background_busy`): `store.migrate` → `instruments.bootstrap_gc1` → the one `pipeline.Worker` (notifier = the notification store, **store-only** hub corrections `hub.corrections_provider`, never the phase-1 file per job; `on_final` wakes the exporter and refreshes `sample_cache`) → `exports.HubExporter(notifier).start()` → outside the lock, `seed_gc1_corrections` (first start: gc1's 11 factors from the phase-1 file via `instrument_admin.seed_gc1`, notified; a missing/invalid file leaves gc1 `pending_corrections`, never zeros) → `Maintenance` (retries the gc1 seed every 10 minutes while unseeded; nightly `store.backup_nightly` once per local day from 1 AM, notified on failure and retried hourly; `store.jobs.prune_done` of jobs older than 30 days). Hands the exporter to `hub_admin`/`instruments_api` `set_exporter`.
- **`hub_control.py`** — the hub tray's server side (Blueprint): open `GET /api/hub/status` (`status_snapshot()`: version, state, processing/updater pause, queue sizes from a cache a background thread refreshes every 5 s with a 0.25 s busy timeout, `stale`, CPU %/RSS via psutil, staged update; not activity), and `POST /api/admin/hub/pause-processing|resume-processing|stop`, **local only** (`netctx.is_local()`: loopback peer and `Host`, no forwarding header, so never through the tunnel; the session gate lets these and `POST /api/restart` through without a session only then), then same-origin, JSON, 64 KiB, admin password. The status carries `hub_url` (the effective hub address, read by the refresher) for the tray's Open in browser. Pause persists `settings_kv["hub_processing_paused"]` (`hub.start` honours it; `HubRuntime.pause/resume`), raises a notification and applies on a thread (202); while paused `background_busy` ignores due jobs. Stop answers 409 `{busy}` during a QBench upload, admin job, running job, export append or diagnostics build unless `force`, then writes the updater's `paused` marker, `restart_policy.request_stop()` (never self-respawn) and exits; Start is the updater's `resume`. The tray itself is `tray/` (`hub_tray.pyw` + `gc_tray/`: pure logic in `logic.py`, tested in `tests/tray` on Windows too; DEPLOY.md "Hub tray on ASAPSV1").
- **Live updates** (v4.0; spec `docs/superpowers/specs/2026-09-30-ui-redesign-live-setup-design.md`) — **`live.py`** (stdlib): an in-memory ring of 1,000 events with a random `boot_id` and a `seq`; `publish(kind, payload)` is thread-safe, never raises, and is called only after the commit, by the pipeline (`submit`, Worker, reprocess, Export to LIMS, release, Replace), `ingest_api` (heartbeat, agent command, token), `instrument_admin`, the notification store, the exporter, `hub_control` and the QBench upload record. **`GET /api/live?since=<boot_id>:<seq>`** (session, not activity) answers from memory only: the ids changed since the cursor (or `reset`), the agent snapshot and hub state from `hub_control`'s refresher cache (`live_agents`, `live_hub`, `note_agent`), and the notification count. **`static/js/live.js`** (`window.GCLive`) polls it (3 s visible, 30 s hidden); the main page merges changed rows fetched with `/api/files?ids=` in place, and has no Refresh button. Every GET a page makes on its own (the live follow-ups) goes through `GCLive.bgFetch`, which sends `X-GC-Background: 1`: such a GET (never a POST, `web_auth.is_background_request`) is not activity and never touches the session's `last_seen`.
- **`hub_admin.py`** — admin Blueprint (JSON + admin password on every call): `POST /api/admin/load-folder` runs `jobs.load_folder` as a background admin job (`AdminJobs`, one job of any kind at a time, polled with `POST /api/admin/jobs/status`, stopped with `/api/admin/jobs/stop`; a finished job carries `summary` and `result: {summary}`), the v1 history import `POST /api/admin/import-history/dry-run|start|last-run` (`jobs.import_history` on the same runner, the dry run too since v3.0.1 (kind `import-history-dry-run`; request errors 400/404 still answered at once); the page's *Import v1 history* panel polls it), `POST /api/admin/exports[/<id>/adopt|new-path|write-fresh]` on the running exporter (refusals are 409 `{error, reason}`), and the page `/admin/hub`.
- **`purge.py`** (v4.0) — *Purge instrument data*: `POST /api/admin/purge/preview|start` on `hub_admin` (admin password; start is an `AdminJobs` job of kind `purge`, confirmed by typing `confirmation_text`: `PURGE <name>`, `PURGE <name> (<id>)` when two instruments share the name), plus session-only `GET /api/purge/status` (`{job, journal}` reduced by `purge.public_job`/`public_summary` to state, phase, counts, times and a name, so the page shows a running or last purge on load; paths, warnings, kept files, lab IDs and addresses only through `POST /api/admin/purge/status` with the password), scope `all` (also the instrument's conflicts with no sample) or `backfill`. It pauses that one instrument (`pipeline.pause_instrument`: the Worker's `claim_next` skips its jobs, `submit` raises `InstrumentPaused` → ingest 503 + `Retry-After`, which the agent backs off on; operator actions on its samples are NOT paused), waits for its running jobs (never holding a lock), writes a **journal** `purged/<inst>-<ts>/manifest.json` (atomic; `pending` → `committed` → `done`, or `abandoned`), `VACUUM INTO backups/pre-purge-<inst>-<ts>.db` (never pruned; deleted when the purge is abandoned), then deletes every row owned by the purged samples in ONE transaction (`_DOOMED` per `OWNER_COLUMNS` table; `KNOWN_REFERENCES` must equal the live schema's references to samples — `sample_references()`, pinned by `tests/test_purge.py`, and `run` refuses an unknown one; a sample a kept row points at is kept) under the exporter's instrument lock, then `HubExporter.after_purge` (idempotent) drops the sidecar's link to the purged ledger row (else the next append refuses `ledger-mismatch`; the CSV is never edited), then MOVES the CDFs to the purged folder (same layout, idempotent per file), never one still referenced (any calibration, `settings.json`'s, a kept revision's `calibration_used.cdf`, a standard, a kept sample/revision/conflict) and never outside `cdf/`. A failure after the commit is `completed_with_warnings`, never a failed job. **`hub.start` runs `purge.recover` before the exporter**, once per process and data folder (`hub.run_startup_recovery`; `hub.start` also runs on a retry and after a failed respawn, while jobs may be live), skipping any journal of a purge live in this process (its instrument paused, or an `AdminJobs` purge owns it): a `pending` journal whose samples all exist is abandoned, a committed one is finished (notified "finished after a restart"); every step is safe to repeat (`tests/test_purge_recovery.py` kills it at each stage). Optional `new_results_path` through `HubExporter.new_path`; an `instrument_events` row only if that table exists; `live` events (the instrument, one `sample` event naming the purged ids). Restore: DEPLOY.md "Restore after a purge" (it rolls back every instrument).
- **Background work vs restart** (v4.0) — `hub_control.busy_reasons()` is the one list (a QBench upload, a report ZIP, any `AdminJobs` job, a diagnostics bundle, running Worker jobs, an export pass) behind the tray's Stop, `POST /api/restart` (409 `{error, busy, blocked}` unless `force: true`; the dry run returns both lists; the Settings button and the tray show them and offer "anyway"), the 3 AM idle check and `/healthz`'s `idle_seconds` (0 while busy, from the cache, so the updater's auto-switch never lands mid-import; contract keys unchanged). `blocking_reasons()` (a purge) is refused even with `force`. At start `hub.start` marks history imports the process died in as `interrupted by a restart` (`import_runs`, whose `counts.progress` is written after each batch), removes the importer's staged copies and notifies; Start resumes with nothing lost (`tests/test_import_interrupted.py`); a run live in this process (`import_history.running`) is never marked. Every `AdminJobs` start goes through `hub_admin.job_refusal`: 503 "the hub is still starting" until `hub.startup_recovered(data)`, 409 while a restart is claimed (`app` registers `set_restart_claimed`) (`tests/test_startup_recovery_live.py`).
- **Running now** (v4.0 lane E; spec "Global status, a way home, and Hub admin") — **`tasks.py`** (stdlib): `tasks.REGISTRY`, an in-memory registry of running work fed by `hub_admin.AdminJobs` (every admin job and `DIAG_JOBS`: kind, instrument, the signed-in name, progress via `tasks.phase_text`), `download_jobs.DownloadJobs(tasks=, download_url=)` (`REPORT_ZIPS`; the owner's one-time link until fetched or expired), the QBench upload thread (`_upload_task_progress`/`_upload_task_end`) and `POST /api/reprocess` (a batch is `watch`ed with `tasks.jobs_probe` on the registry's own thread, never on a request). Feeds never raise into their caller. `GET /api/live` carries `tasks` (`app._live_tasks`: running, plus ended in the last 30 min; no paths, tokens, parameters, summaries or error text; `download_url` only for the owner) and `hub` gains `processing_paused`, `queue: {waiting, running}`, `exports_pending`, `paused_by` (the name, never the address) and `paused_since`. **One agent-liveness rule**: `live.agent_liveness` (live = `last_seen` ≤ 90 s old on the hub's clock); `/api/live` `agents[]` carry `name`, `enabled`, `live`, `last_seen_age_s` (computed at poll time in `hub_control.live_agents`), `GET /api/agents` `live`/`last_seen_age_s`; no page keeps a rule of its own or compares the browser's clock with `last_seen`. An ended task carries `outcome`, one line with its counts built by `tasks._outcome` from numbers only (feeds pass `finish(counts=)`); `open_url` is a hub path only (`_local_url`: never `//host`); `hub.run_startup_recovery` hands what it recovered (purges finished, imports marked interrupted) to `REGISTRY.note_interrupted`, so they show as interrupted tasks for 30 minutes. Purge jobs are `AdminJobs` jobs, so they are tasks too ("Purging GC-x data"; Open → `/admin/hub#purge-panel`). `tasks.BLOCKING_KINDS` (everything but reprocess, whose jobs are durable) is what a restart would cut short: `hub_control.busy_reasons` names any running task of those kinds its own checks missed (`_task_reasons`, once per kind), so the indicator and the restart guard agree (`tests/test_busy_tasks_agree.py`). The shell (`_shell.html` sidebar footer, `_layout.html`) mounts the same `running_now.js`: the running-now row, "N of M GCs live" (`#gc-summary`; the main page's chip uses the same words) and the paused banner (`status_shell.css`). `/api/live` also carries `server_now`/`server_today` (the hub's clock; day headings). `live.js` ignores an agent's age alone for change detection but stamps every agent with `read_at` on every poll: `GCLive.agentAge(agent, now)` = hub age + time since read, `GCLive.agentLive` = the hub's `live` and still within 90 s by that age (pages re-render from these on a timer, never from the browser's clock against `last_seen`; `ui_logic.agentStatus` follows the same rule); it exposes `GCLive.tasks()`/`hub()`/`serverToday()`, and updates carry `tasks`, `boot`, `server_today` and `day_changed`.
- **`diagnostics.py`** — the admin page's *Download diagnostics* bundle (one zip to hand to Claude): `POST /api/admin/diagnostics/estimate|bundle` (admin password; one build at a time, 409) — since v3.0.1 the bundle answers 202 `{job}` and builds on its own runner (`hub_admin.DIAG_JOBS`; the build lock is taken in the request and released by the job; the disk check runs in the job, so not enough disk is a failed job), polled with `POST /api/admin/diagnostics/status` — then a one-time `GET /api/admin/diagnostics/download/<token>` from the finished job's `result.summary` (10 minutes, streamed once, deleted). Manifest/summary (with `hub_control.status_snapshot()`), capped logs, store tables, redacted `settings.json`, a `VACUUM INTO` copy of `gc.db` scrubbed in the copy, export health (a file's tail only when it is provably a hub export), reports, problem CDFs, calibration, the updater's log/config/markers (an allowlist) and the environment. **Secrets never go in**: excluded by name (QBench store, `qbenchlogin.txt`, `admin-setup-code.txt`), known values redacted everywhere (case-insensitive, escaped), secret shapes by pattern (`is_secret_key`: whole words, weak words only in structured forms), and a final pass refuses a zip that still holds one. `diagnostics.busy()` holds off the 3 AM auto-restart and the tray's Stop. Tests: `tests/test_diagnostics*.py`.
- **Sendable links** (v4.0; `sample_links.py`, Blueprint, all session-gated) — `/lab/<lab_id>` (what COA Reviewer links to: `store.samples.with_lab_id`: exact, then ASCII case-insensitive (SQLite NOCASE: é/É stay different), both indexed (`samples_lab`, and `samples_lab_nocase`, which `store.migrate` creates on every start from `store.ENSURED_INDEXES`, outside the numbered schema steps), never a substring, no row limit; the newest `injection_dt` among final runs, else among all, across instruments; the URL decoded once, by the server), `/samples/<id>[/compare[?standard=]|/data]` and `GET /api/lab/<lab_id>` (`{lab_id, sample_id, runs}`). ## QBench gotcha (caused a production outage)

`qbench_pdf_uploader._api_lookup` does `from qbench_client import QBenchAPIClient`. It must resolve the **local** `qbench_client.py` (on `sys.path` because `app.py` is run from its own folder, with `cwd=current` by the updater). Do **not** reintroduce any `sys.path.insert` to an external share path (the old `…\COA Reviewer\V2\Past Data Manager\API`) — that dir is gone and importing from it took uploads down. `tests/test_qbench_import.py` guards this.
